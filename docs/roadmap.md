验收时使用[语法回归样例](regression-cases.md)，分别记录「格式正确」「语法判断正确」「显示位置正确」，三者不能互相替代。更复杂的分栏精读和结构树等 B 实测后再决定。

## 一键反馈

不再等待 B；已上线（PR #21、#22、#25、#28）。内容超过 6000 字符时分两步「① 复制反馈内容」「② 打开 GitHub 粘贴 →」，链接保留真实标题（PR #28）。使用预填 GitHub Issue，保留提交前预览（折叠、只读），用户填写问题类型和说明，由用户最后点击提交；现阶段不引入数据库。只包含用户确认的原句、分析结果、模型名和应用版本，绝不包含密钥、请求头或浏览器存储内容。长结果可复制到正文，避免把大段数据全部塞进链接。

公开仓库的 Issue 会公开，点击前明确提示用户检查句子是否含个人信息；不要求姓名、邮箱。预填链接本身也会把内容带到 GitHub，因此预览确认要发生在打开链接前。README 的「不保存」说明已区分正常分析与主动反馈。

首条真实错误已于 2026-10-28 收到（Issue #27）；PR 2（#34）已合并，但上线实测未通过，#27 在 PR #37 合并时被自动关闭，2026-11-02 复测后再次重新打开；2026-11-03 复测通过后关闭；PR-A 已完成，PR-B1 已完成，接下来依次做 PR-B2、PR-C。流程：用户反馈 → Issue → 小范围修复 → PR 写 `Fixes #编号`，合并时自动关闭 → 上线复测，没修好就 Reopen。不把用户的敏感原句直接加入公开测试；必要时改成保持同类语法问题的虚构句。Issue 模板允许「不确定正确答案」，不要把反馈门槛设成先会纠错。

- 难点强化：先考虑用户主动标记「没看懂」，仅存在本机浏览器；点击次数不直接等同于没学会。反馈与学习记录分开处理。

- 推广与作品集：与产品验收分开管理；先形成一次真实反馈到修复的完整记录，再整理介绍与演示。
