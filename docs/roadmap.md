## 可视化按 A → 实测 → B 推进

1. **任务 A：点击修饰语，高亮它修饰的词。** 已合并（#14），待上方人工验收。分支 `feat/modifier-highlight`，可选字段 `modifies`。先明确「中心词」与「整个短语」的指向含义，再实现。重复词按位置定位；再次点击取消；详细结构开关、换句和清空不能留下高亮。
2. **A 合并并实测后再做任务 B：从句括号条带，可嵌套。** 分支 `feat/clause-brackets`，保留平铺 `segments`，新增可选 `clauses` 范围。手机换行与大字模式必须可读，主干默认仍保持简单。

两个任务开始前统一位置约定。建议采用句内 `segments` 的零起始索引、范围右端不包含，空格片段也计入；这是待落实的设计建议，不是当前接口已支持的承诺。若任务 A 需要指向片段中的单词，应先决定拆分片段还是使用字符范围，不能仅按相同文本匹配。

新增字段不合规时只丢弃该字段或该项，不拒绝整个结果，也不为它们触发付费修正。A 应拒绝越界、自指和不适用的引用；B 应拒绝越界与交叉范围，允许正确包含。异常条目不能连带删除独立有效项。

验收时使用[语法回归样例](regression-cases.md)，分别记录「格式正确」「语法判断正确」「显示位置正确」，三者不能互相替代。更复杂的分栏精读和结构树等 B 实测后再决定。

## 一键反馈：A、B 均合并后

首选预填 GitHub Issue，保留提交前预览与编辑，由用户最后点击提交；现阶段不引入数据库。只包含用户确认的原句、分析结果、模型名和应用版本，绝不包含密钥、请求头或浏览器存储内容。长结果可复制到正文，避免把大段数据全部塞进链接。

公开仓库的 Issue 会公开，点击前明确提示用户检查句子是否含个人信息；不要求姓名、邮箱。预填链接本身也会把内容带到 GitHub，因此预览确认要发生在打开链接前。上线时同步修改 README 的「不保存」说明，区分正常分析与主动反馈。

首条真实错误：用户反馈 → Issue → 小范围修复 → PR 写 `Fixes #编号` → 合并后验证。不把用户的敏感原句直接加入公开测试；必要时改成保持同类语法问题的虚构句。Issue 模板允许「不确定正确答案」，不要把反馈门槛设成先会纠错。
