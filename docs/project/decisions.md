## 2026-11-01

- **任务 B 的待定项全部确认，分两个 PR 实施。**
  做法与理由：
  - 长从句拆分条件：超过 6 个英文单词，或内部包含嵌套从句时，要求模型拆出内部主语、谓语及其他必要成分；短从句可以保留为一个片段。只含介词短语不是强制拆分条件，不为增加框数量逐词拆分。词数口径沿用应用现有英文词数规则（缩写和连字符一致）。
  - 仅「显示详细结构」开启时画出从范围条带；默认主干视图保持简洁。英文下方细线 + 编号，对应下方编号从句清单，第一版不加点击、折叠或悬停交互。同句现有成分标签、引线和条带要留出空间，不互相覆盖。
  - 第一版支持定语从句（relative）、宾语从句（object）、状语从句（adverbial）；状语从句可带 time、condition、reason、concession、purpose、result、comparison、manner 小类，不确定时只写「状语从句」。最多三层嵌套。单片段短从句不画条带，但仍在清单里显示。
  - 多个时态：主句优先，然后按从句在原文中的顺序；相同组合只写一次。这是模型输出要求，不在本地靠字符串重排猜测主句，`tenseReason` 也要能区分主句和从句。
  - 数据结构：保留平铺 `segments` 与原文逐字覆盖，新增可选句级 `clauses`（`start` 含、`end` 不含，空格标点计数）；不让模型输出 id、depth、编号、重复原文或 parent。交叉的两项都丢，最外层为第 1 层，超过 3 层的内层项丢弃；候选超过 200 项时忽略整句 clauses。任何 clauses 错误只影响该可选信息，不抛 `AnalysisValidationError`，不触发付费修正。
  - **PR 1（`feat/clause-data`）**：clauses 校验/归一化、SYSTEM 规则、时态规则、反馈从句清单、文档与测试。不写长从句强制拆分提示词，不画条带，不写 `Fixes #27`。
  - **PR 2（`feat/clause-brackets`）**：长从句拆分提示词、`level` 规则（主句主干 core，从句内部拆分成分 detail）、详细视图条带、多层轨道、跨行绘制与重排清理。PR 1 经独立审核并合并后，才从最新 main 新建分支，PR 写 `Fixes #27`；真实模型和上线实测仍由负责人完成。
  验收原则不变：写代码的工具不验收自己的 PR；PR 1 的自动检查不等于真实验收。

  做法：模型输出 {type,subtype?,text}，text 去掉首尾空白后在 segments 片段边界上唯一精确匹配；无匹配、多处匹配、起止在片段中间、缺少 text、text 超过句子长度或无字母数字时丢弃该项，只有 start/end 的旧格式也丢弃。匹配后收掉范围首尾不含字母数字的片段，内部仍是 {start,end,type,subtype?}。同范围去重、交叉两项都丢、最多三层、超过 200 项整句忽略；错误不抛 AnalysisValidationError、不触发付费修正。修改仅限 clauses，modifies、predicateOf、核心校验和客户端渲染不变；demo 与归一化夹具仍用内部范围。版本为 2026-11-02.3。真实模型括号层数、范围和清单仍由负责人上线实测，不能把模拟通过当作语法验收。
- **收紧主句宾语从句 core 主干例外的边界，客户端不按从句类型改 level。**
  原因：PR #36 合并后的虚构长句真实复测，两次都把定语从句里的宾语从句成分标成 core。SYSTEM 新增反例：She thanked the nurse who said that the results were good. 中 the results、were、good 都是 detail；只有直接充当主句谓语宾语的宾语从句适用 core 例外，被任何定语从句、状语从句或另一个从句包住都不适用。默认只显示 She thanked the nurse。
  延续 2026-11-02 锚点决定，旧条目保留；不再让模型数从句下标。Issue #27 写入关闭关联，但真实验收未通过时应重新打开。

## 2026-11-03（level 试点验收与付费修正诊断）

- **默认视图加从句数量提示。**
  原因：#27 复测时负责人也误判过「没有括号 / 没有清单」，实际上是在默认视图下看的。默认视图只显示主干，不画条带、不显示清单，用户会以为分析失败。加一行提示说明从句数量，引导用户勾选详细视图。仍保持「第一版不加点击、折叠、悬停交互」。
  做法：`<p class="clause-hint">`，与 `.structure-note` 同一视觉层级，颜色用现有 muted 变量。N = sentenceClauses(sentence).length（含单片段短从句）。详细视图、无从句、从句全部非法时都不显示。

- **PR #38 level 结构化试点通过及格线，后续规则按同样方式逐节结构化（PR-C）。**
  负责人用 deepseek-flash 真实复测：嵌套宾语从句成分 5/5 不为 core，样例 09 默认视图 2/2 不倒退。样本少，不代表稳定；无法区分拆分改善是判断顺序还是随机波动。原句已在正例中的样例 09 只证明没倒退。
- **付费修正的报错附带第一处不一致位置与附近原文。**
  原因：长句首次格式失败时，泛化的「拼接必须相等」提示可能使付费修正逐字返回相同错误内容。拼接和 sentence.text 对原输入的逐字校验失败时，reason 附句内零起始字符位置、JSON 引号包围的原文/实际结果短上下文；拼接错误还给相邻片段下标。按转义后的长度缩短上下文，确保完整诊断与修正提示不超过 280 字符。校验不放宽，不自动补空格或标点；最多 1 次修正，界面提示不变，reason 原文不展示给用户、不进入反馈正文。沿用原有修正消息，不改 SYSTEM、请求参数或修正流程。版本为 2026-11-03.2。
- **后续顺序：修正诊断定位 → PR-B → 讨论 modifies 原文锚点 → PR-C 穿插其后。**
  PR-B 把 clauses 写进 JSON 骨架并先输出，同时试 temperature；modifies 下标在长句里经常错一位，是否改为原文锚点需另立决定，尚未授权实施；PR-C 延续分节结构化方法。clauses 偶发整段漏输出和长句格式偶发失败记录在路线图，不因试点通过而视为已消除。

## 2026-11-03（PR-B 拆分与 temperature 实验）

- **PR-B 拆成两个 PR：先 temperature（B1），再 clauses 骨架（B2）。**
  原因：两个改动同时上，无法区分效果来自哪个。负责人用 2026-11-03.2 测 #27 原句 3 次，clauses 字段 3/3 有输出（累计漏输出 1/8），骨架要解决的问题样本太少；而同一输入 1 次整段不拆、2 次完整拆开，随机性更突出。B1 只加请求参数，SYSTEM 不改一个字；B2 在 B1 实测后再做。

  DeepSeek 官方参数文档给出默认 1.0，并按用途推荐：代码/数学 0.0，数据清洗/分析 1.0，通用对话与翻译 1.3，创意写作 1.5；文档未说明本任务属于哪一类，也未注明适用的模型与模式。结构化 JSON 加逐字照抄原文最接近代码/数学，因此只试 0 一个值。思考模式下 temperature 不生效，本项目为非思考模式。风险：取值越低，同一输入的结果越接近固定；若最可能的输出本身是错的，会稳定地错。不通过就回退为不设 temperature。修正请求复用同一请求体。
